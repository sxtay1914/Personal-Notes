## Identify drawbacks
### GPT
1. centralisation of stack (state machine runtime)
2. enterprise monolith, everything is tightly coupled together so it is hard to evolve
3. state explosion, real enterprise system is exception heavy & async & multi-departmental, hard to model as state machines
4. distributed system complexities overlooked, concurrency conflicts, any rollback mechanisms
5. harness itself becomes centralised failure point 
    * counterargument: (prevent failures from overflowing to other systems, contained failures within the system)
6. human escalation becomes the bottleneck

Overall verdict:
Technically feasible, but need to consider:
* reliability 
* maintainability 
* schema change 
* maintenance of state-machines 

### Gemini
1. Rigidity trap, real world operations are messy and throw up cases that don’t fit exactly in predefined states 
2. Heavy deployment and maintenance overhead, because need to re-engineer and redesign the schema
3. Most enterprise company has legacy systems which are hard to be converted to schema. To adapt the schema-approached, a new approach is needed.
4. vulnerability to schema drift when connecting to external 3rd party API that can change the schema and throw errors. Designing a schema to accommodate to different

Sacrificing adaptability for predictability
